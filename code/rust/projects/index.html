有哪些公司在用 Rust？我把它查成一張清單

程式設計・2026/10/13
先講結論：Rust 不是「有人開始試試看」而已——作業系統核心、雲端骨幹、加密與驗證元件這些最不能出錯的地方， 早就換過去或正在換。下面每一項都附官方來源；查不到具體數字的，我直接寫「查無」而不是拿別人的轉述來湊。

這頁是 〈Rust：最受推崇的語言，卻只有 14.8% 的人在用〉 的延伸。 那篇談的是「落差」，這頁談的是「那 14.8% 是誰」。

作業系統與平台

Linux 核心

Rust 支援於 2022 年 12 月的 v6.1 併入主線（官方文件原文「merged in v6.1」）。陸續併入的 Rust 驅動包含 Android Binder、null block 的 rnull、Arm Mali 的 Tyr GPU 驅動。維護者是 Miguel Ojeda，在官方 MAINTAINERS 檔掛名「RUST [GENERAL SUPPORT]」。
重點數字：核心程式碼逾 3000 萬行；策略是「新程式碼用 Rust」而不是改寫舊的
⚠️ 核心仍以 C 為主，Rust 是增量新增；兩種語言互通的成本高。
官方來源：https://docs.kernel.org/rust/index.html

Microsoft Windows

微軟每年指派的 CVE 裡約 70% 是記憶體安全問題。官方自述曾用 Rust 實驗性重寫一個 Windows 低階系統元件（未具名），2024 年起推動讓 Rust 成為驅動開發的 first-class 語言（cargo-wdk 上架 crates.io）。
重點數字：約 70% 的 CVE 屬記憶體安全問題
⚠️ 官方沒有公布「已改寫哪些具體元件」的完整清單。
官方來源：https://www.microsoft.com/en-us/msrc/blog/2019/11/using-rust-in-windows

Google Android

作業系統程式碼從 C/C++ 轉向 Rust。2025 年記憶體安全漏洞占比首度降到 20% 以下；Rust 程式碼的記憶體安全漏洞密度比 C/C++ 低約 1000 倍；Rust 改動的 rollback 率低 4 倍、code review 時間少 25%。
重點數字：76% → 24%（六年）→ 2025 首度低於 20%；漏洞密度差約 1000 倍
⚠️ 這是 Android 的數字，不等於所有專案都會有同樣效果。
官方來源：https://blog.google/security/rust-in-android-move-fast-fix-things

Google Chrome

官方分析 2015 年以來 912 個 high／critical 漏洞，發現約 70% 是記憶體安全問題、其中一半是 use-after-free。2023 年起正式支援在 Chromium 引入第三方 Rust 函式庫。
重點數字：70% 高嚴重性漏洞是記憶體安全問題（912 個的樣本）
⚠️ 目前是「可以引入」而不是整包重寫。
官方來源：https://www.chromium.org/Home/chromium-security/memory-safety/

雲端、網路與協作

Cloudflare（Pingora）

自己用 Rust 寫了 HTTP proxy 取代 NGINX。官方數字是這份清單裡最有說服力的：每秒服務逾 1 兆次請求，同流量下 CPU 少約 70%、記憶體少約 67%；某大客戶的連線重用率從 87.1% 提升到 99.92%，對來源站的新連線減少 160 倍；每天為客戶省下 434 年的 handshake 時間。
重點數字：每秒 1 兆請求；CPU −70%、記憶體 −67%
⚠️ Rust 的非同步生態複雜、學習曲線陡，不是每個服務都值得。
官方來源：https://blog.cloudflare.com/how-we-built-pingora-the-proxy-that-connects-cloudflare-to-the-internet/

AWS（Firecracker / S3 ShardStore）

微 VM 服務 Firecracker 從 2017 年就用 Rust 寫；S3 的儲存節點 ShardStore 也是 Rust，官方說自動化推理驗證「只需多約 13% 程式碼」（傳統形式證明常要多達 10 倍成本）。
重點數字：ShardStore：驗證只多約 13% 程式碼
⚠️ S3 由 300+ 個微服務組成，Rust 只是其中一部分。
官方來源：https://aws.amazon.com/blogs/storage/how-automated-reasoning-helps-us-innovate-at-s3-scale/

Discord

Read States 服務從 Go 改寫成 Rust。Go 版每隔幾分鐘就會出現延遲與 CPU 尖峰（因為 Go 至少每 2 分鐘強制觸發 GC）；改寫後尖峰消失，快取容量提升到 800 萬筆 Read States。
重點數字：快取容量 800 萬筆；延遲尖峰消失
⚠️ 毫秒級的延遲對比官方只有圖表、沒有文字數字，所以這裡不寫具體毫秒。
官方來源：https://discord.com/blog/why-discord-is-switching-from-go-to-rust

Dropbox

桌面同步引擎（代號 Nucleus）整個重寫，花了約 4 年，已對全體用戶上線。
重點數字：歷時約 4 年，全體用戶已上線
⚠️ 官方沒有提供效能數字，所以這裡不寫。
官方來源：https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine

Meta

原始碼版本控制系統 Mononoke 自 2019 年起是 monorepo 的正式後端、以 Rust 撰寫。2019 年內部 Rust 開發者超過 100 人，官方說有「數百名開發者寫下數百萬行 Rust」。
重點數字：100+ 位開發者；後來開源的 Sapling 也是 Rust
⚠️ 是內部系統，外面看不到完整規模。
官方來源：https://engineering.fb.com/2021/04/29/developer-tools/rust/

產品與工具

1Password

1Password 8 的跨平台核心框架完全以 Rust 撰寫，包含業務邏輯、資料模型與密鑰管理。
重點數字：核心框架完全 Rust（官方確認）
⚠️ 網路常引用的「50 萬行 Rust、600 個 crate」查無官方出處，本頁不引用。
官方來源：https://blog.1password.com/1password-8-the-story-so-far/

Shopify

採用 Rust 作為官方系統程式語言並加入 Rust Foundation。也把 CRuby 的 JIT 編譯器 YJIT 從 C 改寫成 Rust（原本 C 版約 11,000 行），隨 Ruby 3.2 上游化。
重點數字：YJIT 原 C 版約 11,000 行，改寫後上游進 Ruby 3.2
⚠️ 是「系統層採用」，不是整個電商平台都用 Rust。
官方來源：https://shopify.engineering/shopify-rust-systems-programming

Figma

多人協作的同步伺服器改寫成 Rust。序列化時間快逾 10 倍；Rust 記憶體用量極低，可以為每一份文件各開一個獨立的 Rust 子程序。官方也提到舊的 TypeScript 伺服器有 GC 造成的延遲尖峰。
重點數字：序列化快逾 10 倍
⚠️ 前端仍然是 TypeScript，改的是同步伺服器。
官方來源：https://www.figma.com/blog/rust-in-production-at-figma/

我自己在寫這頁之前也重跑過一次覆核：6 個抽查裡 5 個完全一致，uv 差 1（查詢之間有人按了星星），API 回 HTTP 200 沒有被限流。

我查不到的部分（照實說）

  • Discord：毫秒級的延遲對比，官方只有圖表、沒有文字數字 → 這頁不寫具體毫秒。
  • Dropbox：同步引擎重寫後，官方沒有提供效能數字 → 不寫。
  • 1Password：網路常見的「50 萬行 Rust、600 個 crate」找不到官方出處 → 不引用。
  • Apple：記憶體安全走的是硬體 MTE ＋ 安全配置器（Memory Integrity Enforcement，iPhone 17 全面開啟、涵蓋逾 70 個用戶態程序），不是用 Rust。放在這裡是為了對照，不是說 Apple 也用。
