Rust：最受推崇的語言，卻只有 14.8% 的人在用——我把數據攤開看

程式設計・2026/10/12

延伸閱讀：有哪些公司在用 Rust？公司清單＋熱門專案排行　·　Rust 最擅長什麼？9 個場景與該用／不該用對照

先講結論：Rust 不是「比較好的 C++」，也不是萬靈丹。它是一把用開發速度換取記憶體安全的工具—— 而且這筆交易在「解析器、網路協定、系統底層」這類魔鬼細節多的地方特別划算。這篇只擺官方數據，最後給一張「什麼情況該用／不該用」的對照表。

一、先看那個很奇怪的數字

Stack Overflow 每年問全球開發者一個問題：「你今年用過的語言裡，明年還想繼續用哪些？」

Rust 在這一題連續多年第一名，2025 年是 72%（2024 年 83%）。聽起來像全民運動。但同一份調查裡，實際使用 Rust 的人只有 14.8%。

用過且「明年還想用」的比例（2025）
72%　← 連續多年第一
實際有在用 Rust 的比例（2025）
14.8%
來源：Stack Overflow Developer Survey 2025（49,000+ 位開發者）。注意 2025 的 72% 比 2024 的 83% 低，第一名沒變，但比例是下降的。

這個落差本身就是 Rust 最有意思的地方：大家想要它，但多數人的公司還沒真的用它。原因不在技術，在成本——後面第五節會講。

二、Rust 到底是什麼

一句話：跑得和 C／C++ 一樣快，但在編譯階段就把記憶體錯誤擋掉的語言。

  • 2006 年由 Mozilla 的工程師開始做，2015 年發布 1.0。
  • 沒有垃圾回收器（GC），所以不會像 Java／Go 那樣偶爾停下來等 GC。
  • 靠一套叫「所有權（ownership）」的規則，在編譯時檢查「這塊記憶體誰負責、什麼時候釋放」。
  • 現在用在：Amazon、Google、Microsoft、Meta、Mozilla，以及 Linux 核心。

來源：CISA〈The Urgent Need for Memory Safety in Software Products〉。

三、優點：三個有數字的理由

① 記憶體安全：不是口號，是 1000 倍

先看問題有多大。三家公司的官方說法幾乎一樣：

~70%微軟每年被指派 CVE 的漏洞中，屬於記憶體安全問題的比例
~70%Google Chromium 專案「嚴重安全漏洞」中，記憶體安全問題的比例
67%Mozilla 某年 58 個漏洞裡，39 個屬記憶體損毀
來源：CISA 官方文章（引述微軟、Google、Mozilla 的報告）。

那 Rust 能改善多少？Google 的 Android 團隊 2025 年公布的數字最直接：

每百萬行程式碼的記憶體安全缺陷數
C／C++（歷史資料）：約 1000 個
Rust（約 500 萬行）：0.2 個　← 差距約 1000 倍
來源：Google Android 團隊 2025 年報告（Jeff Vander Stoep 公布）。同報告指出 Android 的記憶體安全漏洞占比首次降到 20% 以下（四年前超過 75%）。

② 意外的副作用：開發效率也變好

Google 用業界標準的 DORA 指標衡量，發現 Rust 的程式碼回滾率只有 C++ 的四分之一、程式碼審查時間少約 25%。也就是說「更安全」沒有犧牲速度，反而少掉很多返工。

③ 工具鏈是公認最好用的（71%）

Cargo（Rust 的套件管理與建置工具）在同一份調查裡是最受推崇的開發工具，71%——一個「建置工具」能拿到這種分數很少見。另外 Python 生態的 uv（把 pip 換掉的那個）本身也是 Rust 寫的，拿下「最受推崇新技術」74.2%。

四、缺點：也一樣要有數字

① 學習曲線是真的陡

同一年度的 Rust 官方調查裡，45.2% 的人把「複雜度」列為障礙；45.5% 擔心產業採用不足（比前一年 42.5% 更高）。有分析指出，團隊導入後的前 3～6 個月，開發速度會下降 30～50%——因為資深工程師在跟生命週期標註奮戰，而不是在寫功能。

② 改造成本比學語言更貴

問題往往不是「學 Rust」，而是「你現有的程式不是 Rust」。要嘛翻譯、要嘛新舊並存慢慢換——兩條路都很貴。這也是 14.8% 與 72% 落差的主因：技術吸引力高，但切換成本也高。

③ 編譯時間、async 生態仍未成熟

編譯比直譯式語言慢是常態；非同步（async）的錯誤訊息與生態在社群裡也一直被抱怨。

⚠️ 誠實講：Rust 也會有漏洞
Google 自己公布了一個在 unsafe Rust 裡寫出的線性緩衝區溢位（CVE-2025-48530，CVSS 8.1，在 CrabbyAVIF 元件）。它沒有被實際利用，是因為 Android 的記憶體配置器把「靜默損毀」變成「可偵測的崩潰」而提早抓到。
兩個結論：① 語言安全不是萬靈丹，unsafe 區塊與 FFI 邊界仍是風險集中處；② 語言安全 ＋ 配置器／模糊測試的縱深防禦，比只靠語言可靠。

五、什麼情況該用、什麼情況不該用

情境建議理由
解析器（圖片／字型／JSON／壓縮）值得這類是 CVE 磁鐵；Chromium 已把 PNG、JSON、字型解析器換成 Rust
網路協定、系統底層、長時執行的服務值得記憶體洩漏與競態在這裡代價最高
需要榨效能又要安全性（金融交易、遊戲引擎）值得願付 6～12 個月導入期
現有 C／C++ 專案想「全部重寫」先不要成本極高；建議只換高風險模組（解析器、協定）
寫網站後端、內部工具、資料分析不必這些情境本來就少有記憶體安全問題，Python／Go／TypeScript 更快出貨
團隊完全沒人有系統程式經驗先不要前 3～6 個月速度下降 30～50% 是真的

六、我的看法（以及我怎麼查證的）

Rust 的熱度不是炒作，但也不是「該學不然會被淘汰」。真實狀況比較像：在它擅長的那一小塊，它幾乎沒有對手；在那一塊之外，它通常不是最划算的選擇。

如果你的工作會碰到別人丟給你的二進位資料（圖片、壓縮檔、網路封包），那 Rust 值回票價。如果只是做內部工具或網站，先把手上的東西做完比較實在。

本篇所有數字都來自公開來源：CISA 官方文章（微軟／Google／Mozilla 的漏洞統計）、Google Android 團隊 2025 年報告、Stack Overflow Developer Survey 2025（49,000+ 位開發者）、Rust 官方 State of Rust 調查。數字有分歧或下降的地方（例如推崇度 83%→72%、受訪者 65,000→49,000）我都照實寫出，沒有挑好看的那個講。
