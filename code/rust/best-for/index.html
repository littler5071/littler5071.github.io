Rust 最擅長什麼？9 個場景與該用／不該用對照

程式設計・2026/10/13
先講結論：Rust 不是「比較好的 C++」，也不是萬靈丹。它是一把用開發速度換取記憶體安全的工具， 而且這筆交易在「解析器、網路協定、系統底層」這類魔鬼細節多的地方特別划算。 這頁把 9 個場景攤開，每個場景都附來源，也附「什麼情況不適合」。

搭配看：〈有哪些公司在用 Rust？〉（誰在用、熱門專案排行）與 〈Rust 完整分析〉。

九個場景

1. 作業系統核心與底層

核心程式的記憶體錯誤往往直接變成高風險漏洞，Rust 在編譯期就擋掉 use-after-free、空指標、緩衝區溢位，而且不犧牲 C 的效能特性（沒有 GC、行為可預測）。

代表專案：Linux 核心 Rust 支援、Android Binder 驅動

來源：https://docs.kernel.org/rust/index.html
⚠️ 注意：核心仍以 C 為主，Rust 是增量新增不是重寫；兩種語言互通的成本很高。

2. 記憶體安全的關鍵基礎設施

這類元件「處理來路不明的網路資料」，是攻擊面最大的地方，歷史上卻多為 C/C++ 寫的。Prossimo 統計指出 60–70% 的 iOS／macOS 漏洞屬於記憶體安全漏洞。

代表專案：Firefox 的 Quantum CSS（Stylo）、Rustls（TLS）、Hickory（DNS）、sudo／su、curl 可選 Rustls

來源：https://www.memorysafety.org/
⚠️ 注意：不是所有元件都值得重寫——curl 的 HTTP（Hyper）整合就已終止支援，只剩 TLS 用 Rustls。

3. 高併發網路服務與代理

非同步、多執行緒、沒有 GC → 高併發下延遲穩定、資源用量低，同時降低對外服務的攻擊面。

代表專案：Cloudflare Pingora（每秒逾 1 兆請求，CPU −70%、記憶體 −67%）

來源：https://blog.cloudflare.com/how-we-built-pingora-the-proxy-that-connects-cloudflare-to-the-internet/
⚠️ 注意：Rust 的 async 生態複雜、學習曲線陡；流量不大、團隊不熟 async 時，Go／Python／Node 的總成本可能更低。

4. 命令列工具

這類工具是「CPU 密集的批次處理」：掃大量檔案、解析、比對。Rust 編成原生機器碼、沒有 GC、沒有直譯器啟動開銷，加上成熟的平行處理，又快又能編成單一靜態執行檔（安裝不必裝依賴）。

代表專案：ripgrep（比 GNU grep 約快 10 倍）、uv（比 pip 快 8–10 倍，有快取 80–115 倍）、Ruff（比 Flake8／Black 快 10–100 倍）

來源：https://astral.sh/blog/uv
⚠️ 注意：只有「經常執行、對速度敏感」的工具才值得重寫；Rust 編譯時間較長，迭代開發體感較慢。

5. WebAssembly

Rust 原生可編成 wasm32，輸出小、啟動快、沒有 GC，適合把高效能邏輯（影像、解析、加密、邊緣運算）搬到瀏覽器。

代表專案：Rust and WebAssembly 官方書、wasm-pack、HuggingFace Candle 的純瀏覽器 WASM 範例

來源：https://rustwasm.github.io/docs/book/
⚠️ 注意：wasm32-unknown-unknown 之下部分標準函式庫不可用（println! 沒作用、std::fs 會出錯、不能開執行緒）；複雜 DOM 操作仍得靠 JS 橋接。

6. 資料庫與儲存引擎

儲存引擎是「極度效能敏感 ＋ 資料正確性關鍵」的元件，Rust 的零成本抽象、可控制記憶體佈局與並行安全很契合。

代表專案：TiKV（分散式 KV）、sled（嵌入式）、Qdrant

來源：https://tikv.org/
⚠️ 注意：主流資料庫（PostgreSQL、SQLite、MySQL）仍以 C/C++ 為主，並未改用 Rust；TiKV 仍高度依賴 C 寫的 RocksDB，是「Rust 外殼 ＋ C 核心」。「Rust 資料庫已全面超越傳統資料庫」查無權威來源支持。

7. 遊戲引擎

遊戲對效能與記憶體佈局極度敏感。Rust 的 ECS（資料導向設計）快取友善、易於大規模平行；沒有 GC 就不會有垃圾回收造成的畫面卡頓。

代表專案：Bevy（官方建議設定後約 0.8–3.0 秒完成編譯，對比其他 Rust 引擎「改一個換行要 30 秒以上」）

來源：https://bevy.org/
⚠️ 注意：Bevy 仍是早期階段引擎，編輯器、資產工具鏈、第三方生態遠不如 Unity／Unreal；3A 專案目前仍以 C++ 引擎為主。

8. 資料處理與大數據

資料分析是「大量資料 ＋ 大量平行計算」。Rust 核心能做到多核心自動平行、向量化查詢，還能處理超過記憶體大小的資料（out-of-core 串流），並以 Apache Arrow 欄式模型提高快取效率。

代表專案：Polars（官方列舉 Out of Core、Parallel、Vectorized Query Engine、GPU 支援）

來源：https://docs.pola.rs/
⚠️ 注意：Pandas 生態成熟、教學資源多，Polars 的 API 不完全相容，遷移有學習成本；而且常是「Rust 核心 ＋ Python 介面」，使用者寫的還是 Python。

9. AI／機器學習（誠實版）

Rust 的價值不是取代 Python 做訓練，而是在三個地方：① 資料前處理與 tokenization；② 推論與部署；③ 訓練框架裡的高效能元件。

代表專案：HuggingFace tokenizers（Rust 實作再包成 Python）、Candle（Rust ML 框架，可編到 WASM）

來源：https://github.com/huggingface/tokenizers
⚠️ 注意：模型訓練目前仍以 Python／PyTorch 為絕對主流，Rust 訓練工具相對年輕；「Rust 已能取代 PyTorch 做主流訓練」查無權威來源支持——網路上那種個人報告屬非權威來源，本頁不引用。

該用 Rust vs 不該用 Rust

該用（✓）不該用（✗）
對記憶體安全極度敏感的基礎設施：OS 核心、TLS、DNS、瀏覽器引擎、代理 想「整體重寫」既有大型 C/C++ 專案——互通成本高、風險大，通常只做局部替換
高頻執行的原生命令列工具：ripgrep、uv、Ruff（快 10–100 倍、單一靜態檔免依賴） 一次性小工具或雛形驗證——用 Python 腳本更快寫完，Rust 開發與編譯成本不划算
CPU 密集、需要平行與可預測延遲的高併發網路服務 團隊不熟 async／Rust，而且流量不大的服務——Go／Python／Node 總成本可能更低
需要編到 WebAssembly 的高效能元件（影像、解析、加密、邊緣運算） 想快速迭代的專案——Rust 編譯時間較長、生態較小，開發迭代體感較慢
資料分析引擎層（Polars）、推論與 tokenization 等 AI 基礎設施層 模型研究與訓練——目前仍以 Python／PyTorch 生態為主，別用 Rust 重新造輪子

  • AI 場景：查無權威來源支持「Rust 已能取代 PyTorch 做主流訓練」。

一句話帶走

如果你的程式會碰到別人給你的資料（圖片、壓縮檔、網路封包、指令輸入），而且跑得夠頻繁， 那 Rust 值得學；如果你只是想快點把功能做出來、流量也不大，先用手上順的那個語言就好。
