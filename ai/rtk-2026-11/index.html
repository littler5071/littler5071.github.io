一句話結論

RTK 是「命令輸出壓縮器」：它不減少你問 AI 的問題，只把 git status、ls -la、ps aux 這類雜訊多的輸出縮小後再交給模型。實測確實能省 57～94% 的輸出位元組，但這不等於省下同樣比例的帳單；而它會改寫你 agent 執行的指令、並可選擇性攔截 LLM API，安裝前要先決定你信任它到什麼程度。

一、原理：四個步驟，一行指令

ROUTE → EXECUTE → FILTER → PRINT
  1. ROUTE：看指令名稱（git／cargo／pytest／docker／kubectl…）決定用哪個過濾器，支援 100+ 指令
  2. EXECUTE：真的執行原指令，取得 stdout／stderr／exit code
  3. FILTER：只留「有用的部分」——去掉進度條、ANSI 色碼、重複行；相同行折成次數；超過上限就截斷
  4. PRINT：輸出精簡版，並在必要時附上「被省略的內容怎麼取回」的提示

關鍵設計（實測驗證）：

  • 失敗不壓縮：gcc -c bad.c 失敗時，258 bytes 的完整錯誤訊息原樣保留，exit code 1 也保留
  • 省略可回收：截斷時輸出會附 rtk recall <hash>，實測用該 hash 確實取回被藏起來的 275 行
  • 本機執行：strace 追蹤顯示執行期間沒有任何對外 TCP 連線

三、怎麼接進 AI 代理（也是風險起點）

rtk init -g            # 寫入 Claude Code 的全域 hook
rtk init -g --opencode # OpenCode
rtk init -g --codex / --gemini / --agent cursor …

裝好後，代理執行 git status 時，hook 會偷偷改寫成 rtk git status，模型只看到壓縮後的結果。

實測 rtk rewrite 的行為：

你下的指令被改寫成
git statusrtk git status
cat notes.mdrtk read notes.md

它不只處理「輸出」，還會把 cat 換成自己的 read——這代表它會改變指令語意，不只是換個顯示方式。

逃生門（實測存在）：

  • export RTK_DISABLED=1 → hook 直接放行，不再改寫
  • rtk proxy <cmd> → 跳過過濾，拿原始輸出
  • 可在設定加 denylist，指定哪些指令不准改

四、安全性評估（逐項）

項目實測結果風險
對外連線strace -f -e trace=connect：沒有任何對外 TCP（無論有無同意 telemetry）低
遙測（telemetry）預設關閉，需 rtk init 時明示同意；RTK_TELEMETRY_DISABLED=1 可硬關；實測狀態顯示 consent: never asked / enabled: no低（但要確保安裝時不誤按 y）
遙測內容官方文件列：版本、OS、arch、指令名稱（最多 5 個）、節省量、裝置雜湊；明列不收集原始碼、完整指令參數、路徑、金鑰中低（仍會透露「你用哪些工具」）
本機資料~/.local/share/rtk/：history.db、recall.db（含被省略的完整輸出，可能包含檔案內容）中：輸出被存到磁碟，敏感 repo 的內容會落地
改寫你的 agent 設定rtk init 會寫 ~/.claude/hooks/、.cursor/hooks/、.gemini/hooks/ 等；升級 binary 不會自動更新舊 hook中高：hook 是供應鏈信任邊界
LLM Proxy（rtk-proxy）獨立 binary、另附授權；可把代理指向本機 proxy（ANTHROPIC_BASE_URL），記錄 rtk-proxy.db、rtk-proxy.log高（若啟用）：它會看到完整 prompt 與回應
授權rtk 本體 Apache 2.0；proxy 另授權需自行確認商用條款

版本演進提醒

有開發者回報：舊 hook 會讓代理用 rtk proxy 繞過過濾、把完整錯誤輸出讀回來（等於繞過壓縮），而且升級 rtk 不會替換既有 hook。要確認你的 hook 有呼叫 rtk rewrite，否則行為會與新版不一致。

五、最容易被誇大的地方：省 token ≠ 省錢

RTK 自己的文件就寫明三件事：

  1. 它省的是「bash 輸出」，而 bash 輸出只是 input token 的一部分（還有系統提示、對話歷史、你的 prompt）
  2. input token 也只是帳單的一部分（output token 另計）
  3. rtk gain 的 token 數是 bytes ÷ 4 估算，不是真的 tokenizer 計數

第三方實測（Quesma，Terminal-Bench 2.1，每題跑 5 次對照）：

  • 成本變化：Fable 降 5%、DeepSeek 升 5%，等於沒有顯著差異
  • 但完成題目所需回合數約減半
  • 原因：現代代理大量使用 Read／Grep／Glob 這些原生工具，不經過 shell，RTK 攔不到

換句話說：RTK 真正的價值是「少一點噪音、少幾輪往返」，不是「帳單直接打八折」。

六、適合誰、不適合誰

情境建議
你的代理大量跑 git／cargo／docker／測試，且輸出很吵值得裝，實測省 57–94% 位元組
你主要用 Read／Grep 讀檔案（像 Hermes 現在的做法）效益有限——那些工具不經過 shell
處理敏感 repo（金鑰、客戶資料）先想清楚 recall.db 會把輸出落地；建議關掉 recall 或指定較小保存期
想接 LLM Proxy 來統計成本先確認授權與資料流向；它會看到完整 prompt
只想省錢不要期待；第三方基準顯示成本變化在 ±5% 內

七、我的結論與建議

這工具沒有惡意行為的證據（無對外連線、遙測預設關、失敗輸出完整保留、可完整停用），但它是「會改寫你代理指令」的工具，屬於信任邊界上的東西，不是單純的顯示優化。

給這台機器的建議：

  1. 不裝全域 hook。Hermes 目前主要用 Read／Grep 工具，RTK 攔不到，效益低。
  2. 若要試，用手動模式：只在雜訊大的指令前面加 rtk（例如 rtk ps aux、rtk ls -la），不改任何設定。
  3. 永遠設 export RTK_TELEMETRY_DISABLED=1，並定期檢查 ~/.local/share/rtk/recall.db 大小。
  4. 想省成本，優先順序應該是：減少不必要的工具輸出 → 用便宜模型做粗活 → 最後才考慮壓縮層。
