AI 助理實測 · 桌面自動化

不看圖也能操作電腦？用「無障礙樹」讓 AI 點按鈕

同樣是「讓 AI 幫我點按鈕」，一條路是截圖猜座標，另一條路是直接問作業系統：這個按鈕叫什麼、能不能按、在哪裡。這篇把兩條路的成本攤開，並附上在這台 4 GB Ubuntu 上的實測數字。

0.69s列出 22 個應用程式

一、兩條路的差別，不在新舊，在資料來源

截圖派：拍一張畫面 → 視覺模型猜「按鈕在 (x, y)」→ 點下去。模型看到的是像素，座標是它「估」出來的。

無障礙樹派：直接問作業系統「這個視窗裡有哪些元件、叫什麼、能不能按、在哪個位置」→ 拿到結構化 JSON → 依元件的 ref 操作。這套資料本來是給螢幕閱讀器用的，AI 只是撿現成。

一句話：一個從像素反推語意，一個直接拿語意。標準元件（按鈕、輸入框、選單、清單）是後者的主場。

二、四個平台各有一層無障礙 API

平台API誰提供拿到的東西
WindowsUI Automation（UIA）系統內建（Win32／WPF／UWP）元件樹、ControlType、Name、AutomationId、Invoke／Value／Toggle
macOSAXUIElement系統內建，要在「輔助使用」授權AXRole、AXTitle、AXChildren、AXPosition、AXPress
LinuxAT-SPI2（走 D-Bus）at-spi2-core；GTK／Qt 應用都會掛上去role、name、state、位置、可執行動作
網頁Chromium accessibility tree（CDP）瀏覽器AX 節點樹；Playwright 的 aria snapshot 就是這條

前提是：元件要「有發佈無障礙資訊」。GTK／Qt／Win32／WPF 通常都有；Electron 要開旗標；Canvas、遊戲、自繪介面、遠端桌面畫面沒有。

三、代表實作：agent-desktop

這次研究的主體是 vercel-labs/agent-desktop（CLI ＋ C library，Apache-2.0）。它的設計有幾個關鍵：

  • 不是代理：它沒有內建模型，只負責「看」與「做」，observe → act → verify 由呼叫它的 AI 自己跑。
  • 預設語意操作：透過無障礙 API 動作，不移動滑鼠、不搶焦點；加 --headed 才用實體輸入。
  • ref 機制：snapshot 回傳 JSON，每個可操作元件都有 ref（像 @s8f3k2p9:e8）；畫面一變就回 STALE_REF，不會拿舊座標亂點。
  • 明確定位：只做桌面原生應用，不做網頁（網頁交給它的 agent-browser）。

同一條路上還有 Microsoft 的 UFO²（UIA＋視覺混合、允許代理在隔離桌面跑）與 macOS 的 a11y-mcp，做法不同但原理一致。

四、跟截圖派比：成本差在哪

項目截圖派無障礙樹派
每步輸入一張 1080p 圖，約 1.1k～1.5k tokens一棵樹的 JSON：小對話框 436 bytes（約 100 tokens），複雜 app 數 KB
定位模型估座標，常差 10～20 px直接拿元件座標／ref，不會偏
速度截圖＋上傳＋推理，2～6 秒／步本機讀樹 0.7～1.7 秒，模型只處理文字
文字讀取靠 OCR／視覺，易錯字元件 name／value 原字
盲點看得到就能點沒有無障礙資訊的介面完全看不到

五、本機實測（Ubuntu 22.04／X11／4 GB）

A. 桌面層：agent-desktop 1.2.0

測試結果數字
version成功1.2.0／linux x86_64
list-apps成功0.69 秒／22 個應用
list-windows成功約 0.8 秒
snapshot --app zenity成功一次1,708 ms／436 bytes／1 個節點（button OK）
snapshot --app gnome-calculator失敗3.9 秒後 WINDOW_NOT_FOUND，同時計算機 core dumped
snapshot --app gedit逾時8.7 秒無回應

根因寫在 log 裡，不是猜的：

at-spi2-registr[1551]: got RegisterEvent with invalid signature 'sass'

at-spi2-core 2.44.0-3（Ubuntu 22.04 內建）的 registryd 拒絕 agent-desktop 送出的簽章，接著 GTK 應用在註冊事件時直接 SIGABRT。所以：只查清單沒問題（那兩條只讀 registry），一讀整棵樹就掛。這是平台版本不相容，不是 CLI 邏輯錯。

B. 瀏覽器層：CDP 無障礙樹（同一台機器）

測試結果
取得整棵 AX 樹30 個節點，32 ms
精簡成 role＋name264 bytes（7 個語意節點：heading／status／textbox／4 顆 button）
用 role＋name 點 7×8＝259 ms，結果 56（正確）
對照那 4 顆按鈕的真實座標是 x=54、y=208 等——截圖派要自己猜這些數字
264 bytes 的文字 vs 一張 1.1k～1.5k tokens 的圖；32 ms 取樹 vs 2～6 秒一步。這就是兩條路的實際差距。

六、限制（先講清楚）

  1. 看不到沒有無障礙資訊的介面：Canvas、遊戲、遠端桌面、Java Swing 舊程式、部分 Electron。
  2. ref 會過期：畫面一動就 STALE_REF，每一步都要重新 snapshot，也代表每一步都要一次模型呼叫。
  3. 權限很大：能看到輸入框的值、清單內容、郵件主旨，隱私風險跟截圖派一樣高。
  4. 提示注入：樹裡的 name／value 也是文字，一樣可能被當指令，不可逆動作要人工確認。
  5. 平台差異大：macOS 要授權、Windows 同權限層免授權、Linux 對工作階段健康度很敏感。
我們最後怎麼用
  • 瀏覽器端：走無障礙樹（CDP Accessibility），本機實測 32 ms 可用。
  • 桌面端：這台 Ubuntu 22.04 的 at-spi 版本卡住，退回截圖派；換機或升 24.04 再處理。
  • 原則：能拿語意就拿語意，拿不到才看圖。
