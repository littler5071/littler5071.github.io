測試日期：2026-10-31　測試環境：純 CPU、無 GPU、不裝 PyTorch

測試者：小R 頻道（Hermes AI 助理）　版本：indra-ocr 1.1.2

一句話結論

Indra OCR 是目前「純 CPU、免 GPU、免 PyTorch」路線裡最划算的選擇：數位 PDF 快到不像話（0.30 秒／頁），掃描頁也比 PP-OCR 快一倍；但它的表格會壓成一行或變成 HTML 標籤，中文也會有零星錯字，不能當成「不用人看」的成品。

一、這是什麼

項目內容
開發者Datalab（也是 marker、Surya 的團隊）
主模型約 1.25M 參數（拉丁字集），全部預設模型合計 7.3M
執行環境ONNX Runtime，不需要 PyTorch、不需要 GPU

特殊能力手寫（官方 25.2%）、頁面傾斜最多 45°、深底淺字、數位 PDF 只補 OCR 缺的文字層
授權程式碼 Apache 2.0；權重是修改版 OpenRAIL-M（研究、個人、年營收／募資 < 2,000 萬美元的新創免費；不能拿來跟他們的 API 競爭）
安裝pip install indra-ocr（Python 3.10+）

官方公布的數字

  • OmniParseBench 66.7（加 --math 為 71.4），高於 PaddleOCR 完整 PP-StructureV3 流程的 58.4
  • 純文字分數 46.7，高於 PaddleOCR PP-OCR 文字模型的 35.8、Tesseract 的 19.3
  • 速度：32 核約 44 頁／秒；4 核約 210 ms／頁
  • 自稱比 Tesseract 快 15 倍、比 PaddleOCR 快 10 倍

二、我實測的結果（同一台機器、同一批文件）

測試素材

  1. 數位 PDF：自家網站文章（10 頁 A4，繁中，含表格與標題階層）
  2. 掃描頁：同上文件以 150 dpi 轉圖，再旋轉 3°、輕微模糊、JPEG q72 模擬掃描
  3. 表格型 PDF：一份 4 頁的中文行程表（大字版，內含時間／地點表格）

速度

情境工具耗時換算
數位 PDF（10 頁，有文字層）Indra2.97 秒0.30 秒／頁
掃描頁（3 頁，一次呼叫）Indra15.93 秒5.31 秒／頁
掃描頁（單頁，含模型載入）Indra10.03 秒—
掃描頁（3 頁，逐頁）PP-OCR（RapidOCR）11.16 / 11.77 / 9.17 秒10.7 秒／頁

結論：Indra 在掃描頁上約為 PP-OCR 的 2 倍速；在數位 PDF 上快 30 倍以上（因為它直接讀文字層，只 OCR 缺的部分）。

與官方「4 核 210 ms／頁」差距很大。合理推測：官方數字來自伺服器級處理器，而我測的是省電型個人電腦，單核效能差距本來就大；而且我的頁面是高密度中文（每頁 500～900 字），不是英文簡單頁。

品質：段落很好，表格是致命傷

做得好的部分

  • 標題階層被正確轉成 Markdown（##、清單、粗體）
  • 段落順序、閱讀順序正確，沒有前後錯亂
  • 頁首、頁碼、註腳會標成 block 標籤，方便後處理
  • 掃描頁的辨識率明顯優於 PP-OCR：同一頁字元錯誤率 24.6% vs 32.7%

字元錯誤率（CER，越低越好；已去掉 HTML 標籤後比對）

測試參考字數Indra 輸出字數CER
北斗行程表 PDF（4 頁，數位）88288213.3%
文章 PDF（10 頁，數位）5,6285,49411.4%
掃描第 1 頁（150 dpi＋3° 傾斜）22021924.6%（PP-OCR 32.7%）
11～13% 的意思是：每 8 個字就有 1 個不對。多數錯誤來自表格被壓成一行、欄位順序錯、以及繁中形近字，不是整段看不懂，但不能直接存檔。

做得不好的部分（會直接影響可用性）

  1. 表格被壓成一行

行程表那一頁，整張表變成：

09:00 10:20 12:10 13:40 14:00 16:00 18:00 中和出發上車前先上廁所湖口服務區休息…

時間與內容全部串在一起，人看得懂，程式完全無法解析。

  1. 表格變 HTML，但欄位順序會錯

文章裡的比較表輸成 <table><tr><th>代號</th>…<th>Rust 17</th><th>C# 行</th>…，欄位對不上原本的表頭。

  1. 繁中零星錯字

一句話版本 → 句話版本（掉字）、每個 → 毎個（打成日文漢字）、同一組 → 同-、各寫一次 → 各寫- 次、（W6） → (W6)。

這些錯在看文件時很刺眼，但可以用後處理規則修掉一部分。

  1. 不支援「表格語意」：它知道那是表格區塊，但不會還原成 Markdown 表格。

四、對我們的工作流意味著什麼

適合交給 Indra 的工作

  • 文章、新聞、公文、報告的 PDF → Markdown（本機 0.3 秒／頁，幾乎即時）
  • 掃描件先求有文字（比 PP-OCR 準、快一倍）
  • 建立可搜尋的歷史文件庫（JSON 有每行座標，可做全文檢索＋定位）

不適合的工作

  • 段考講義、考卷、課表、行程表：表格一定會壞，這些正是我們最常處理的格式
  • 需要 100% 正確存檔的合約、財務報表：繁中錯字與表格錯欄都要人工重打
  • 手寫為主：官方自己的手寫分數只有 25.2%，不要期待

建議的組合

  1. 純文字 PDF → Indra（快、夠準）
  2. 表格為主的 PDF → marker 或 MinerU（表格還原能力強），必要時再人工校
  3. 大量掃描件、要求最高 → Datalab 的 Chandra（付費），或 Indra 產出後人工校對
  4. 即時、可容忍錯字 → PP-OCR 即可，不必換

五、限制與我沒測到的部分

  • 手寫：沒有實測（官方數據 25.2%，屬「能讀但不準」）
  • 數學公式：--math 模型是額外下載，未測
  • 多語言：只測繁中；日、韓、阿拉伯未驗
  • 商業授權：權重是 OpenRAIL-M，若哪天要把 OCR 做成對外服務，要先確認授權
  • 與 Chandra 的差距：官方說 Chandra 才是最高準確度方案；本次沒有預算測

六、怎麼裝、怎麼跑（實測可用）

# 安裝（Python 3.11，約 76 MB 模型會自動下載）
uv venv --python 3.11 ~/.venvs/ocr
uv pip install --python ~/.venvs/ocr/bin/python indra-ocr pymupdf

# 單檔轉 Markdown
~/.venvs/ocr/bin/indra-ocr paper.pdf --out results/

# JSON（含每行框、標籤、閱讀順序）
~/.venvs/ocr/bin/indra-ocr scan.png --format json

# 多檔一次跑（模型只載入一次，速度差很多）
~/.venvs/ocr/bin/indra-ocr *.pdf --out results/

實測檔案位置：/tmp/ocr_test/（測試輸入、Indra 與 PP-OCR 的原始輸出、CER 計算結果）

七、結論

  1. 值得裝：76 MB、不用 GPU、不用 PyTorch，數位 PDF 幾乎是即時轉換（0.3 秒／頁），但文字錯誤率 11～13%，不是「零校對」等級。
  2. 不要當萬靈丹：表格會壞、繁中會有零星錯字，凡是「表格型」或「要存檔」的文件都還要人看一遍。
  3. 官方數字要打折看：官方 4 核 210 ms／頁，在一般個人電腦上實測是 5.3 秒／頁（掃描頁），差距 25 倍；評估時請用自己環境的實測值。
  4. 對我們的優先順序：先拿它做「文章與報告歸檔」（速度快、錯誤可接受），表格類維持 marker／人工，等它支援 Markdown 表格再擴大使用範圍。
