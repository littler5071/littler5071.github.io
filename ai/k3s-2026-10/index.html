第 0 層：先搞懂三個名詞（30 秒版）

0.1 Kubernetes（K8s）是什麼

想像你有一批貨櫃（應用程式），跟幾十台卡車（伺服器）。
Kubernetes 是那個「碼頭調度中心」：你只說「我要 3 個這個貨櫃一直在跑」，它就負責找車、裝載、檢查、壞了重派、要換版本時一台一台換。

具體一點，它做的事是：

你說的 K8s 幫你做的
「這個服務要 3 份」 自動在有空位的機器上開 3 個容器，掛掉一個就補一個
「更新到新版本」 一台一台換（滾動更新），新版本壞了就自動退回舊版
「這台機器掛了」 把上面的工作搬到其他機器重開
「這兩個服務要互相找得到」 給每個服務一個固定名稱與內部 IP，不用記機器 IP
「這個服務要對外 80 埠」 透過 Ingress／LoadBalancer 幫你轉進去
「這份設定／密碼」 用 ConfigMap／Secret 管理，不用寫死在映像裡

它跟 Docker Compose 最大的差別：Compose 是「一台機器上幫你啟動一組容器」；K8s 是「一群機器上，持續把系統維持在你宣告的狀態」——機器掛掉、容器當掉、要擴充、要換版，它會自己處理。

0.2 那 K3s 又是什麼

K3s 就是 Kubernetes，只是「打包方式」不一樣。

標準的 Kubernetes 要你自己湊齊很多零件（etcd 資料庫、API server、排程器、控制器、CNI 網路、DNS、Ingress、負載平衡、儲存），每個零件都是一個獨立程式、各自有版本、各自要設定憑證。

K3s 把這些全部塞進一個不到 100 MB 的執行檔，並在裡面附上：containerd（容器執行環境）、Flannel（網路）、CoreDNS（DNS）、Traefik（Ingress）、ServiceLB（負載平衡）、local-path（儲存）、以及預設用 SQLite 當資料庫。

所以：

  • K8s 是規格與功能（API、YAML、Pod、Service、Deployment… 全部一樣）
  • K3s 是「把 K8s 裝起來變簡單」的一種發行版（像 Ubuntu 之於 Linux）
  • 你寫的 kubectl 指令、Helm chart、Operator，在 K3s 上完全通用

0.3 為什麼它的定位是「太難養」而不是「功能不夠」

Kubernetes 的功能其實非常夠。問題出在養它的成本：

  • 建一個能用的叢集，要處理 9 類基礎設施（憑證、資料庫、runtime、CNI、DNS、Ingress、LB、儲存、版本對齊）
  • 憑證過期 → 整個叢集連不上；etcd 磁碟滿 → 叢集寫不進去；升級順序錯 → 起不來
  • 這些事的知識門檻高，而且出錯時很難查

這就是官方首頁那句 “Situations where a PhD in K8s clusterology is infeasible” 的意思——不是 K8s 不夠強，是它的維運門檻把大多數人擋在外面。K3s 要解決的就是這一件事：把「裝起來、維持運作、升級」變成一行指令級的操作。

第一層：入門（它是什麼、為什麼會存在）

1.1 名字的由來

Kubernetes 是 10 個字母，縮寫 K8s（中間 8 個字母）。K3s 想做的是一個「記憶體只有一半」的版本，於是取中間 3 個字母 → K3s。官方明說：沒有長寫法、也沒有官方唸法。

1.2 沒有 K3s 之前，裝一套 K8s 有多麻煩

用 kubeadm 從零建叢集，你至少要處理這些事：

項目 傳統 K8s 的痛點
憑證 CA、apiserver、kubelet、etcd 憑證要自己產、自己輪替，過期就全叢集掛掉
資料庫 要自己架 etcd 叢集（3 或 5 節點、quorum、defrag、快照）
容器執行環境 要自己裝 containerd 或 CRI-O，設 cgroup driver
CNI 要自己選 Calico／Cilium／Flannel 並部署
DNS 要自己裝 CoreDNS
Ingress 要自己裝 ingress-nginx／Traefik
LoadBalancer 裸機沒有雲的 LB，要自己接 MetalLB
儲存 要自己接 CSI 或 NFS
版本 每個元件版本都要對得上，K8s 版本 skew 政策很囉唆

一個熟悉的人做也要半天到一天，而且升級與憑證輪替才是真正的地獄。

1.3 K3s 的做法：把上面全部包進去

K3s 把所有控制平面元件編譯進同一個 process，並且內建這些東西（官方文件「Packaged Components」）：

  • containerd（容器執行環境；也支援 cri-dockerd）
  • Flannel（CNI，預設 VXLAN）
  • CoreDNS（叢集 DNS）
  • Traefik（Ingress Controller）
  • ServiceLB / Klipper（裸機 LoadBalancer 實作）
  • Kube-router（Network Policy）
  • local-path-provisioner（預設 StorageClass，用本機磁碟）
  • Spegel（分散式容器映像 mirror，減少對外拉映像）
  • host utilities（iptables、socat 等）

而且預設資料庫是 SQLite（透過 kine 介面），不是 etcd —— 這是它「單節點就能跑」的關鍵。

1.4 五分鐘上手（單節點）

# 1) 安裝（會自動裝成 systemd 服務）
curl -sfL https://get.k3s.io | sh -

# 2) 看節點
sudo k3s kubectl get nodes
# NAME       STATUS   ROLES                  AGE   VERSION
# k3s-server  Ready    control-plane,master   30s   v1.37.1+k3s1

# 3) 讓一般使用者能用 kubectl
mkdir -p ~/.kube && sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $USER ~/.kube/config && chmod 600 ~/.kube/config
export KUBECONFIG=~/.kube/config

# 4) 部署一個服務
kubectl create deployment web --image=nginx:alpine --replicas=2
kubectl expose deployment web --port=80 --type=LoadBalancer

# 5) 看它拿到什麼 IP（ServiceLB 會用節點 IP）
kubectl get svc web

這樣就有：兩個 nginx Pod、一個 LoadBalancer Service、一個可用的 Ingress Controller，不用裝任何其他東西。

1.5 心智模型：只有兩種節點

  • server node：跑 k3s server，有控制平面與資料庫
  • agent node：跑 k3s agent，只有 kubelet + runtime + CNI

單機時，server 同時也跑工作負載（K3s 不會像 kubeadm 那樣幫 control-plane 上 taint 阻止排程）。

第二層：進階（架構、規格、操作）

2.1 三種部署架構

A. 單 server + 內嵌 SQLite（最常見）
- 1 台 server，0～N 台 agent
- 資料庫就是一個 SQLite 檔（/var/lib/rancher/k3s/server/db/）
- 優點：最簡單、最省資源、備份就是複製檔案
- 缺點：沒有 HA，server 掛了就沒控制平面

B. 3 台以上 server + 內嵌 etcd（HA）
- --cluster-init 啟動第一台，其餘用 --server https://server1:6443 加入
- etcd 必須是奇數台（quorum = n/2+1）
- 官方警告：內嵌 etcd 在慢速磁碟（例如 Raspberry Pi 的 SD 卡）會有效能問題

C. 2 台以上 server + 外部資料庫（MySQL／PostgreSQL／外部 etcd）
- 適合已經有 RDS 之類的企業環境
- K3s 只負責 K8s，資料庫交給專業的

另外有一個實務常用的東西：固定註冊位址（fixed registration address）
多台 server 時，agent 不該寫死連某一台，而是連一個 VIP／DNS 名稱（--tls-san），再由它轉到健康的 server。

2.2 官方資源實測（這是最值得看的表）

K3s 官方 Resource Profiling 頁面，用 Intel Xeon 8375C 2.90GHz 與 Raspberry Pi 4B 實測，跑 K3s v1.26.5 + Prometheus + Grafana + 範例 nginx：

元件 處理器 最小 CPU 最小 RAM（Kine/SQLite） 最小 RAM（內嵌 etcd）
server（含一個工作負載） Xeon 8375C 核心的 6% 1596 MB 1606 MB
server + 1 agent Xeon 8375C 核心的 5% 1428 MB 1450 MB
agent Xeon 8375C 核心的 3% 275 MB 275 MB
server（含工作負載） Pi4B 1.5GHz 核心的 30% 1588 MB 1613 MB
server + 1 agent Pi4B 1.5GHz 核心的 25% 1215 MB 1413 MB
agent Pi4B 1.5GHz 核心的 10% 268 MB 268 MB

兩個關鍵訊息：

  1. 控制平面本身約 1.2～1.6 GB RAM（含監控堆疊與一個 nginx）——「K3s 只要 512MB」是把它當純 agent 或關掉一堆元件時的說法。
  2. CPU 需求真的很低：Xeon 上只吃 5～6% 的一核；Pi4B 上 25～30% 的一核。所以「省」主要省在 CPU 與維運，不是省在 RAM 下限。

官方另外給的最低門檻（不含工作負載）：

節點 CPU RAM
Server 2 cores 2 GB
Agent 1 core 512 MB

2.3 規模上限（官方 sizing 表）

Server CPU Server RAM 可帶 agent 數
2 4 GB 0–350
4 8 GB 351–900
8 16 GB 901–1800
16+ 32 GB 1800+

HA（3 台 server）大約可再多 50%，例如 3 台 4vCPU/8GB 可撐到約 1,200 個 agent。
官方建議 agent 每批 50 台以內加入（加入瞬間有 CPU 尖峰），超過 255 節點要改 cluster-cidr。

2.4 網路與防火牆（實務最常卡的地方）

埠 協定 用途
6443 TCP Kubernetes API（所有節點都要能連 server）
8472 UDP Flannel VXLAN（用 WireGuard backend 時改成 51820/51821）
10250 TCP kubelet metrics（要用 metrics-server 時節點間互通）
2379／2380 TCP 內嵌 etcd 的 server 之間
30000–32767 TCP NodePort 服務

兩個官方明講的安全警告，值得抄進筆記：

VXLAN 的 8472 埠絕對不要對外網開放，等於把整個叢集網段攤在網路上。

Flannel 用 bridge CNI 做 L2 交換，帶有 NET_RAW 的 Pod 可以做 ARP spoofing，官方建議對不受信任的 Pod 套用 restricted PSA profile 關掉 NET_RAW。

2.5 資料庫選擇：SQLite 還是 etcd？

SQLite（kine） 內嵌 etcd 外部 MySQL／Postgres
節點數 只能 1 台 server 3、5、7 台 2 台以上 server
HA ❌ ✅ ✅（資料庫要自己 HA）
備份 複製 DB 檔／停機快照 k3s etcd-snapshot 內建 資料庫自己的備份
效能 單機夠用；寫入是序列化的 好，但寫入密集、怕慢碟 看資料庫
適用 開發、邊緣、單機服務、CI 生產 HA 已有企業級 DB

這是最多人踩的坑：用 SQLite 起了一個「正式」叢集，等到要加第二台 server 才發現加不了，必須重建並遷移資料。

2.6 日常操作速查

# 用設定檔（強烈建議：不要把參數寫在 install script 裡，重跑會覆蓋）
sudo tee /etc/rancher/k3s/config.yaml >/dev/null <<'YAML'
write-kubeconfig-mode: "0644"
disable:
  - traefik          # 不用 Traefik（改自己的 Ingress）
  - metrics-server   # 記憶體吃緊時
tls-san:
  - k3s.example.com
YAML

# 升級（先 server 逐台，再 agent；不可跳版）
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=v1.37.1+k3s1 sh -

# 備份（etcd 模式）
sudo k3s etcd-snapshot save --name pre-upgrade
sudo k3s etcd-snapshot list

# 還原
sudo systemctl stop k3s
sudo k3s server --cluster-reset --cluster-reset-restore-path=/var/lib/rancher/k3s/server/db/snapshots/<file>

# 離線安裝（air-gap）
#  1. 下載 k3s 執行檔 + k3s-airgap-images-<arch>.tar
#  2. 載入映像：sudo k3s ctr images import k3s-airgap-images-amd64.tar
#  3. INSTALL_K3S_SKIP_DOWNLOAD=true ./install.sh

# 自動升級（GitHub 上的 system-upgrade-controller + Plan CRD）
kubectl apply -f https://github.com/rancher/system-upgrade-controller/releases/latest/download/system-upgrade-controller.yaml

版本 skew 規則：升級不能跳過中間的 minor 版本（K8s 政策），system-upgrade-controller 不會幫你擋。

第三層：深入（決策、比較、風險）

3.1 K3s 拿掉了什麼

K3s 不是「K8s 縮小版」這麼簡單，它移除或替換了一些東西：

項目 狀態
舊版 in-tree cloud provider（AWS/GCE/Azure…） 移除，改用外部 cloud-controller-manager
部分 alpha 功能與 feature gate 預設關閉或移除
舊式（非 CSI）in-tree 儲存驅動 移除
內建 etcd（單節點時） 換成 SQLite/kine
多個獨立 process 的控制平面 合併成單一 process
Docker 為預設 runtime 改成 containerd（可選 cri-dockerd）

但它是 CNCF 認證的 conformance 版本：kubectl、YAML、Helm chart、Operator、CRD 這些完全通用，只是「裝法」與「預設值」不同。

3.2 與其他方案比較

方案 定位 優點 缺點 適合誰
K3s 輕量 K8s 發行版 單 binary、內建齊全、ARM 支援好、社群最大 SQLite 單點、預設值偏「方便」而非「安全硬化」 家庭 lab、邊緣、IoT、CI、小型生產
RKE2 安全硬化版（同為 Rancher） CIS benchmark 對齊、預設不包 Traefik、FIPS 取向 較重、學習曲線陡 政府／金融／需要合規
MicroK8s Canonical 版 snap 安裝、addon 生態豐富、桌面開發友善 snap 綁定 Ubuntu、資源比 K3s 重一些 Ubuntu 開發者、單機 lab
k0s 單 binary、零依賴 真的「一個 binary」、預設更中性 生態與文件較小 想要乾淨基底自己加料
Talos 不可變 OS + K8s 極高一致性、API 驅動、安全 不能 SSH 進去、學習曲線最陡 認真做叢集、要 immutable infra
kubeadm 官方安裝器 最貼近 upstream、可控性最高 什麼都要自己做 已有 K8s 團隊、要完全掌控
kind／minikube 本機測試 快、隔離、適合 CI 不適合正式 開發與測試

3.3 什麼時候「不該」用 K3s

老實說，這節比優點更重要：

  1. 你只有一台機器、服務也不多 → systemd + Docker/Podman compose 就夠了，K3s 只是多一層要學。
  2. 你有嚴格的合規要求（CIS／FIPS） → 直接用 RKE2 或託管服務，不要自己改 K3s 預設值改到懷疑人生。
  3. 你的磁碟是 SD 卡或便宜 eMMC → etcd 寫入密集，官方自己說不建議。
  4. 團隊沒人懂 K8s → K3s 讓「裝起來」變簡單，但沒讓「除錯」變簡單。Pod 起不來、CNI 不通、PVC 卡住，這些知識一樣要會。
  5. 規模超大（數千節點、多租戶硬隔離） → 用正式發行版或雲端託管。
  6. 你需要 Windows 節點 → K3s 不支援 Windows worker（upstream 有，K3s 沒有）。

3.4 用了之後的實際效益（可量化的部分）

面向 傳統 kubeadm K3s 差距
初次建置 半天～1 天 5～10 分鐘 約 50～100 倍
控制平面 RAM 約 2 GB 起（etcd + 各元件） 約 1.2～1.6 GB（含監控與範例 app） 約 30～40%
節點 CPU 較高（多 process） Xeon 5～6%、Pi4B 25～30% 單核 明顯較低
憑證管理 手動／需工具 自動產生、自動輪替（單 process 內完成） 幾乎免維運
升級 每個元件分別升 一行指令、先 server 後 agent 大幅簡化
備份 etcd 快照自行規劃 k3s etcd-snapshot 內建 內建
映像拉取 每個節點各自對外 Spegel P2P mirror 减少對外依賴 邊緣場景差很多

最容易被低估的效益是「可重建性」：因為安裝是宣告式的（config.yaml + 安裝腳本），整台機器掛掉時，重建時間從「一天」變成「十幾分鐘」。這對家庭 lab 與邊緣部署的價值，遠大於省下的那幾百 MB 記憶體。

3.5 風險清單（含緩解）

風險 影響 緩解
SQLite 單點 server 掛 → 控制平面停擺（工作負載還在跑） 生產用 3 節點 etcd；或接受停機並定期備份 DB
etcd 寫入密集 + 慢碟 叢集隨機卡頓、leader 頻繁切換 SSD；Pi 用外接 SSD（官方明講）
升級跳版 API 不相容、無法啟動 一次升一個 minor；先用 --dry-run 在測試叢集驗證
預設 Traefik 與自架 Ingress 衝突 80/443 被佔用 --disable traefik 或改用 IngressClass
ServiceLB 佔用主機 80/443 與既有 nginx/apache 衝突 改 NodePort、或 disable servicelb
VXLAN 8472 對外 叢集網段暴露 防火牆封鎖；只在內網
NET_RAW Pod ARP spoofing／橫向移動 Pod Security restricted profile
secrets 未加密 etcd/DB 被偷 → 憑證外洩 啟用 --secrets-encryption
容器映像供應鏈 拉進惡意映像 私有 registry + 簽章（cosign）＋限制 image pull policy

3.6 建議的落地路線（從 PoC 到生產）

Phase 0（1 小時）：在一台可犧牲的 VM 上跑單節點，部署 nginx + 一個 PVC，確認 Ingress 與儲存可用。

Phase 1（半天）：把一個真實的小服務搬上去（有狀態的用 local-path PVC，無狀態的用 Deployment），量測：
- kubectl top node 的實際 RAM／CPU
- 重開機後服務是否自動回來
- 備份／還原演練一次

Phase 2（1～2 天）：3 台 VM 做 HA（--cluster-init + etcd），測：
- 關掉一台 server，API 是否仍可用
- 升版流程（先 server 逐台、再 agent）
- etcd 快照還原

Phase 3（選配）：GitOps（Flux／Argo CD）+ 映像掃描 + 備份自動化。到這裡才是「可以放正式服務」的狀態。

3.7 什麼樣的小型環境適合、什麼樣不適合

以下是「低規格主機」的常見判斷方式，用規格而非特定機型說明：

規格對照（依官方 Resource Profiling）

情境 需要 RAM 判斷
單節點 server ＋ 1～2 個小服務 約 1.2～1.6 GB 4 GB 機器可行，但要關掉不需要的元件
3 節點 HA（每台 server） 每台約 2 GB 起 建議 8 GB／台，較有餘裕
純 worker（agent） 約 275 MB 2 GB 的小主機就夠

適合的場景
- 只有一台小主機、想學 K8s、或想讓 3～5 個自架服務有「自動重啟、滾動更新」
- 邊緣裝置、門市小主機、CI runner（跑得動就好，不需要 HA）
- 想把「部署方式」標準化成 YAML，之後搬到雲端不用重寫

不適合的場景
- 記憶體 ≤ 4 GB 而且同一台還要跑資料庫、監控、反向代理、桌面或影音處理 → 會長期在換頁邊緣
- 需要控制平面 HA，但只有一台機器
- 團隊沒有人熟悉 K8s 的除錯（Pod 起不來、CNI 不通、PVC 卡住）

判斷原則：K3s 控制平面本身很省 CPU，但記憶體下限約 1.2～1.6 GB 是硬的。先把「現有服務 + K3s 控制平面 + 一個工作負載」加起來，如果超過實體記憶體的 70%，就不要在同機部署，改用第二台機器或雲端。

三條實務路線
- A. 三台便宜 VPS（各 2 vCPU／4 GB）：完整 HA 練習，成本約每月 US$15～30
- B. 一台小主機當控制平面 ＋ 既有機器當 worker：記憶體壓力分散，不需要三台
- C. 本機用 k3d／kind 練習：不碰正式服務，學概念最快
