實測 10 種格式：微軟 MarkItDown 能轉，但中文 PDF 一試就壞

2026-10-26｜小R 頻道｜AI 工具實測

一句話版本：MarkItDown 是微軟開源的「檔案轉 Markdown」工具，Word、Excel、簡報、網頁、電子書、壓縮檔都轉得漂亮；但中文 PDF 會把漢字換成康熙部首（斗 U+6597 → U+2F43），看起來一樣、搜尋卻搜不到，AI 也會讀錯；英文 PDF 空白消失、圖片完全沒有 OCR。

一、它是什麼

MarkItDown 由微軟 AutoGen 團隊開源，目前版本 0.1.9。它的工作很單純：讀檔、抽出文字、整理成 Markdown，輸出的內容可以直接餵給語言模型，或放進 Obsidian 這類筆記軟體。它不做 OCR、不做排版還原、也不描述圖片內容，定位是「批次轉檔工具」，不是「閱讀器」。

項目內容
版本0.1.9（測試環境：Python 3.12 虛擬環境）
支援格式PDF、DOCX、PPTX、XLSX／XLS、HTML、CSV、JSON、XML、EPUB、IPYNB、TXT、ZIP（遞迴）、圖片（僅 EXIF）、網址
主要依賴pdfminer.six、mammoth、openpyxl、pandas、python-pptx、magika
安裝uv pip install 'markitdown[all]'

三、三個坑

坑 1中文 PDF：字變成康熙部首

斗 U+6597 → U+2F43

我拿自己做的中文 PDF（Chrome 產生、標題「北斗二日遊・大字版」）去轉，輸出變成「北⽃⼆⽇遊・⼤字版」——畫面上幾乎看不出差別，但那幾個字其實是康熙部首區的碼位，不是一般漢字。

原本的字轉出變成
斗（U+6597）U+2F43
大（U+5927）U+2F24
日（U+65E5）U+2F47
影響：中文搜尋完全搜不到、AI 讀到的是部首不是那個字、比對與翻譯都會歪。
原因不是檔案壞掉。 Chrome 產生 PDF 時只嵌入用到的字型子集，而把字形對應回 Unicode 的對照表（ToUnicode）並不完整；工具遇到對不上的字，只好退回部首碼位。同一份內容的原始 HTML 轉起來完全正常。
# 一招驗證：轉出的檔案裡有沒有部首字
grep -P '\x{2F43}' out.md   # 有命中就是踩到

# 對照組：同樣的檔案用 pdftotext
pdftotext -layout 檔案.pdf -   # 中文正常

坑 2英文 PDF：單字之間空白消失

Provided proper attribution is provided → Providedproperattributionisprovided

用 arXiv 一篇 2.2 MB 的論文實測，文字抽得出來，但空白全部不見，整段變成一大串黏在一起的字。

影響：關鍵字比對、翻譯、摘要都會出錯；如果你的流程是把論文丟給 AI 摘要，這個問題會直接反映在答案品質上。

坑 3圖片：輸出零個字元，它沒有 OCR

PNG、JPEG 都一樣

不管 PNG 或加了 EXIF 的 JPEG，轉出來都是 0 字元。我另外把 exiftool 13.59 裝起來再試，結果一樣——因為它只讀取特定的中繼資料欄位，並沒有辨識圖片文字的能力。

要處理掃描件或圖片，得另外用 OCR 工具，例如 pymupdf、marker。

六、我做的包裝指令：mdit

原生 CLI 一次只能轉一個檔案，批次很麻煩，所以我寫了一個包裝指令：

# 單檔印出
mdit 檔案.docx

# 單檔存檔
mdit 檔案.pdf -o 輸出.md

# 整個資料夾批次轉換
mdit ~/Documents/報告
  ✓ paper.pdf → md_out/paper.pdf.md
  ✓ 報表.xlsx → md_out/報表.xlsx.md
完成：12 個檔案 → md_out/

批次輸出會保留原始副檔名（報表.xlsx.md），避免同名不同格式互相覆蓋；轉換過程的警告一律導到 /dev/null，畫面只留結果。

八、常見問題

Q：它可以把 PDF 轉成「有表格」的 Markdown 嗎？
A：可以，但要看 PDF 怎麼產生。原生數位 PDF 有機會；掃描件不行（沒有 OCR）。中文 PDF 另外有異體字問題。

Q：那為什麼還值得裝？
A：因為 Office 檔、EPUB、ZIP 的批次轉換真的很省事，而且輸出乾淨。把它當「批次轉換器」，不要當「PDF 閱讀器」就沒問題。

Q：影片裡的 U+2F43 是什麼？
A：那是 Unicode 的「康熙部首」區碼位，字形跟一般漢字幾乎一樣，但程式視為不同字元，所以搜尋會失敗。
